# 0011 Claude Haikuによる候補の仕分けは既定の検索に入れない

状態 承認

## 状況

LLMに回答文を作らせない方針は[0007](0007-no-rag.md)のとおりです。そのうえで、LLMの役割を候補の選別に限れば、少ない費用で精度を上げられるかを確かめました。

rerankerで並べ替えた上位10件の質問と回答の全文、それに問い合わせを[Claude Haiku 5.5](https://platform.claude.com/docs/en/about-claude/models/overview)に渡し、問い合わせに答えている候補の番号を最大3件だけ返させました。回答文は書かせていません。出力は構造化出力で番号の配列に限り、思考は切り、`effort`は`low`にしました。計測はAnthropicのClaude API（モデルID `claude-haiku-5-5`）で行い、スクリプトは`scripts/haiku_eval.py`に置きます。入力は[0012](0012-ranking.md)と同じ言い換え100件の2種類です。

Haikuに2つの役割を試しました。ここでのrerankerは`ruri-v3-reranker-310m`です。

1つ目は1位の正解を選び直す役割です。

| 指標 | 口語の質問 | 短い検索語 |
|---|---|---|
| rerankerの1位が正解 | 0.85 | 0.71 |
| Haikuの1件目が正解 | 0.85 | 0.71 |
| Haikuが選んだ最大3件に正解 | 0.93 | 0.85 |
| Haikuが該当なしと答えた割合 | 0.00 | 0.00 |

2つ目は候補に答えがあるかを判定する役割です。プロンプトでは「話題が近いだけの候補は答えとみなさない」と指示し、答えの有無を先に出力させています。答えのない問い合わせは正解の組を候補から外して作っています。比較のため、rerankerの1位の点数にしきい値を置く方法も測りました。しきい値は同じデータで一番よい値を選んだので、実際より良く見えます。

| 指標 | 口語の質問 | 短い検索語 |
|---|---|---|
| 答えがあるとき、Haikuが答えありと判定 | 0.92 | 0.88 |
| 答えがあるとき、Haikuの1件目が正解 | 0.79 | 0.65 |
| 答えがないとき、Haikuが該当なしと判定 | 0.32 | 0.32 |
| rerankerのしきい値で答えありを通す | 0.82 | 0.73 |
| rerankerのしきい値で答えなしを止める | 0.72 | 0.65 |

最初の計測では、Haikuに回答の冒頭200字だけを渡していました。この条件でも1件目の正解率は0.82と0.77、該当なしの判定は0.27と0.34で、結論は変わりません。そのとき答えがないのに何かを選んだ例から20件を読むと、5件ほどは同じ内容の別のFAQで、実際に答えになっていました。残りの約15件は話題が近いだけで問いに答えていない候補でした。

回答の全文を渡したときの費用は、1回あたり入力約3,200トークン、出力約13トークンで、約0.00033ドルです（入力100万トークンあたり0.10ドル、出力0.50ドル）。応答はp50で約1.3秒、p95で約1.65秒でした。

## 決定

既定の検索は、rerankerで並べ替えた上位10件を表示するところまでにします。Haikuの仕分けは入れません。

答えがあるかどうかは機械で判定しません。上位3件は回答の全文を表示し、該当する回答がなければ問い合わせ窓口へ進む案内を画面に置きます。利用者が上位を読んで判断します。

## 影響

- Haikuのためには、Amazon Bedrockの生成AIのモデルを呼びません。
- 検索の応答時間にLLMの約1.3秒が加わらず、LLMの費用もかかりません。
- 社内の問い合わせの文を生成AIのモデルへ送らずに済みます。並べ替えのために、BedrockのCohere Rerank 3.5へは送ります（[0012](0012-ranking.md)）。
- 1位を選び直す役割では、回答の全文を渡すとrerankerと同じ正解率になりました。答えの有無を判定する役割では、答えがない問い合わせの約7割で話題の近い候補を選びました。判定を厳しくするプロンプトにすると、1位の正解率が口語の質問で0.85から0.79、短い検索語で0.71から0.65に下がりました。
- この結論は、候補10件、`effort`が`low`、思考なしの条件での結果です。思考を有効にした場合や、より大きなモデルでは測っていません。
